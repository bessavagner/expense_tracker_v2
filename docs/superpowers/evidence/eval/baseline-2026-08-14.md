# Extraction baseline — 2026-08-14

The number every future model is judged against. Suite: `extraction`, 7 receipt
cases (see `docs/eval-dataset.md`; the dataset is 7, not the DoD's 10). Raw
per-run output is in the `extraction-*.json` files beside this one.

Both suites were run: `extraction` (7 receipt cases) and `behaviour` (7
conversations scored on the ledger rows they produced), three times each.

## The production baseline

`openai:gpt-5.4` — what production runs today, on both `LLM_MODEL` and
`LLM_ASSISTANT_MODEL`.

| | Extraction | Behaviour |
|---|---|---|
| Score (mean) | **0.886** (n=5) | **0.810** (n=3) |
| Range | 0.83 – 0.97 | 0.71 – 0.86 |
| Spread | 0.14 | 0.14 |
| `money_ok_rate` | 0.914 | — |
| Cost per sweep | $0.187 | $0.430 |
| Latency per call | ~8.6 s | ~4.2 s |

Read the range, not the mean alone. See *Why one run is not a measurement* below.

### One behavioural case fails every time

`hipermacional-six-categories-no-double-count` failed in **all three** runs, and
identically: `ledger total 0 != expected 376.70`, with no row satisfying any of
the six categories. The agent registered *nothing*. That is not variance — it
reproduces — so it is a real defect in handling a six-category receipt, on the
model production runs today, and it is the single biggest item in the
behavioural score.

`billing-month-after-closing-day` failed in one run of three, the same way
(total 0). Worth watching; one of three is inside the noise this dataset shows
everywhere else.

Neither is a harness bug: the other five cases pass on the same code path.

## The candidate that was going to be deployed

Commit `63d9743` moved the production default to `gpt-5.6-terra` on the strength
of its list price — $2.00/$12.00 per Mtok against gpt-5.4's $2.50/$15.00, newer
and 20% cheaper on both axes. Measured:

| | `openai:gpt-5.4` | `openai-responses:gpt-5.6-terra` |
|---|---|---|
| Score (mean) | **0.886** (n=5) | 0.807 (n=4) |
| Range | 0.83 – 0.97 | 0.68 – 0.94 |
| Spread | 0.14 | **0.26** |
| `money_ok_rate` | **0.914** | 0.857 |
| Cost per sweep | **$0.187** | $0.282 |
| Input tokens | 33,700 | 89,339 |
| Latency | **8.6 s** | 11.4 s |

**It is 51% more expensive per receipt, despite the lower per-token price.** It
consumes about 2.6× the input tokens for the identical seven images, which more
than erases a 20% per-token discount. The token ratio was stable across every
run, so this is the one result here that is not in doubt.

On quality there is **no measured gain**: the 0.079 score gap is smaller than
either model's own run-to-run spread, so it does not establish that gpt-5.4 is
better — only that terra is not. Its `money_ok_rate`, the dimension E08 weights
decisively, was lower in every paired run.

**Conclusion: do not deploy the swap.** It fails on the cost argument that
motivated it and shows no compensating quality gain. This also restores E08's
own scope line — *"this epic measures; E09 decides"*. Production is untouched.

## Two failures found before any of the above could be measured

Neither is reachable from the test suite, which runs `TestModel` and never
contacts a provider. The first live call is the one a user makes.

**1. Every gpt-5.6 and qwen call returned HTTP 400.** 21 of 21, two providers,
two unrelated causes — both about tool calling, which every agent here does.
Fixed in `assistant/agents/model_compat.py`; details in `docs/eval-dataset.md`
§ *Provider quirks*. Two consequences beyond the harness:

- Deploying `63d9743` would have 400'd **every receipt upload** — the wedge
  feature — on the first photo. The env-var swap alone would have done it, with
  no code deploy needed.
- `LLM_TIER_ESSENTIAL_FALLBACK` is `openrouter:qwen/qwen3.7-flash`, so the
  Essential tier's fallback was already broken in production.

**2. A model that failed 6 of 7 cases displayed 1.00 on every dimension.**
`overall` divided by all cases attempted; the dimensions averaged only the runs
that came back, so the wider the failure the better the columns looked. qwen
printed a flawless row beside a score of 0.14. Fixed — dimensions now use the
same denominator.

## Why one run is not a measurement

`openai:gpt-5.4`, same seven cases, same code, inside one hour:

| Run | Score | `money_ok_rate` |
|---|---|---|
| control | 0.97 | 1.00 |
| head-to-head | 0.83 | 0.86 |
| repeat 1 | 0.84 | 0.86 |
| repeat 2 | 0.97 | 1.00 |
| repeat 3 | 0.83 | 0.86 |

One case is 14% of a seven-case score and the money invariant is pass/fail per
case, so a single receipt read differently moves the headline by more than the
gap between two serious candidates. In the first head-to-head terra led gpt-5.4
0.94 to 0.83; over the next three runs the order reversed every time.

Any comparison here needs **at least three runs per model**, and a gap narrower
than the spread is unmeasured rather than a close call. Closing the dataset's
seven-of-ten shortfall is the cheapest way to shrink the spread.

## Reproducing this

```bash
RUN_LLM_TESTS=1 POSTGRES_PORT=5433 EVAL_FIXTURES_DIR=~/ledger-eval-fixtures \
uv run python src/backend/manage.py eval_models \
  --models "openai:gpt-5.4" --suite extraction \
  --out docs/superpowers/evidence/eval/<date>.md
```

Swap `--suite extraction` for `--suite behaviour` for the other half.

Total spend for every run recorded here: roughly **$3.40**.

## The decision this baseline produced

Production stays on `openai:gpt-5.4`. The defaults staged in `63d9743` were
reverted in light of the numbers above; migrations `0023` and `0024` were kept,
so the gpt-5.6 family stays priced and E09 can evaluate it without re-seeding.
